# 当前项目架构与成熟网站差距分析（2026-03-20 更新）

## 1. 分析范围与结论摘要

本分析基于当前仓库代码结构与关键实现文件（`index.html`、`Scripts/data.js`、`Scripts/blueprint.js`、`Scripts/blueprint.facade.js`、`Scripts/blueprint.worker.js`、`https_server.py`、`.gitignore`）得出。

一句话结论：
该项目在"业务功能完整度（计算 + 蓝图生成）"上已经很强，但在"工程化成熟度（测试、发布、安全、监控、可维护性）"上仍属于**功能型工具站**阶段，而非"成熟网站工程"阶段。

**新增目标**：部署到 Vercel，增加多语言支持和 SEO 优化。

## 2. 当前架构盘点

## 2.1 技术栈与运行方式

- 前端形态：经典静态页面 + 全局脚本加载（无打包入口）。
- UI框架：Vue 2（通过 `Scripts/vue.min.js` 直接引入）。
- DOM/工具：jQuery 2.2.4 + jQuery插件。
- 数据与业务：`Scripts/data.js`（约 6564 行）承载大部分业务逻辑。
- 蓝图核心：`Scripts/blueprint.js`（约 4024 行）承载蓝图数据结构与编码/解码逻辑。
- 性能优化：蓝图生成已通过 `blueprint.facade.js + blueprint.worker.js` 引入 Web Worker，减少主线程阻塞。
- 部署方式：以静态资源为主，可通过本地 HTTPS Python 脚本运行（`https_server.py`）。

## 2.2 目录职责（核心）

- `index.html`：唯一页面入口，直接加载所有脚本并承载主要 UI 模板。
- `Scripts/data.js`：需求计算、配方处理、UI交互、存储读写、初始化流程。
- `Scripts/blueprint.js`：蓝图结构、建筑/传送带生成、序列化压缩。
- `Scripts/blueprint.facade.js`：蓝图异步外观层、互斥锁、防重复触发。
- `Scripts/blueprint.worker.js`：蓝图计算工作线程。
- `Scripts/data.json`：图标与资源数据。
- `quote/*.html`：说明/更新片段，通过 jQuery `load` 注入页面。

## 2.3 启动与执行链路

1. 页面加载 `index.html`，按顺序同步加载多个脚本（无 `defer/async`）。
2. `data.js` 在 `$(function(){...})` 中执行：
   - 异步请求 `Scripts/data.json` 以准备图标数据。
   - 同时执行 `f_init()` 初始化 Vue 实例、事件绑定、状态加载。
3. 用户触发计算后，核心计算仍由 `data.js` 全局函数体系执行。
4. 用户触发"生成蓝图"时，`BlueprintFacade.generateAsync(...)` 优先走 Worker，失败时降级同步执行。

## 2.4 现有优点（值得保留）

- 业务功能深度高：计算、配方、排除、多方案、蓝图生成等能力完整。
- 兼容性务实：保留同步降级路径，避免 Worker 不支持导致不可用。
- 关键性能点已优化：蓝图重计算已迁入 Worker。
- 项目对纯前端友好，部署成本低。

## 3. 与"成熟网站项目"相比的主要缺口

以下缺口按"成熟网站工程"标准给出，不代表当前项目不可用，而是代表"可持续维护/协作/上线治理"层面的不足。

## 3.1 架构与可维护性缺口

1. **单体脚本过大、职责耦合严重**
   - `data.js` 和 `blueprint.js` 文件体量过大，UI、状态、算法、存储交织。
   - 风险：改动回归范围大，新人接手成本高，缺陷定位慢。

2. **缺少模块化边界与类型系统**
   - 无 TypeScript、无显式模块分层（domain/application/infrastructure/ui）。
   - 风险：隐式数据结构大量流通，重构风险高。

3. **入口与依赖管理较原始**
   - 依赖以静态脚本文件方式手工维护，缺少标准构建流程和包版本治理。

## 3.2 质量保障缺口

1. **无自动化测试体系**
   - 未发现单元测试、集成测试、E2E 测试目录与配置。
   - 风险：每次改动都依赖人工回归，迭代速度和稳定性难兼顾。

2. **无代码质量门禁**
   - 虽有 `.husky` 基础框架，但未配置项目级 pre-commit / pre-push 检查脚本。
   - 未见 ESLint/Prettier/commitlint 等标准化质量规则落地。
   - **已部分完成**：ESLint + Prettier 已配置（A-02 完成）。

## 3.3 发布与运维缺口

1. **无 CI/CD 流程**
   - 未发现 GitHub Actions/GitLab CI 等流水线配置。
   - 风险：构建、测试、发布不可重复，发布质量依赖个人经验。

2. **无环境分层与配置治理**
   - 未见 dev/staging/prod 配置区分机制。
   - 风险：环境差异问题难定位，线上参数变更缺乏可控性。

3. **缺少 Vercel 部署配置**（新增）
   - 无 `vercel.json` 配置文件。
   - 未配置路由规则、缓存策略、安全头。
   - 无 SPA fallback 配置。

## 3.4 可靠性与可观测性缺口

1. **缺少统一错误采集与上报**
   - 业务里有局部 try/catch，但无全局错误治理（JS错误、Promise拒绝、关键路径告警）。

2. **缺少性能监控与用户行为指标**
   - 无 Web Vitals、关键交互耗时、蓝图生成耗时等可观测数据。
   - 风险：性能问题只能"体感判断"，无法持续优化。

## 3.5 安全与合规缺口

1. **前端安全基线不足**
   - 未见 CSP、SRI、权限策略等安全头策略。
   - 依赖库版本偏旧（如 jQuery 2.x、Vue 2.x 的长期维护风险）。

2. **依赖与漏洞治理缺失**
   - 缺少依赖扫描/漏洞告警机制（如 Dependabot 或 SCA）。

3. **安全头配置缺失**（新增）
   - 缺少 Content-Security-Policy (CSP) 配置。
   - 缺少 X-Content-Type-Options: nosniff。
   - 缺少 X-Frame-Options: DENY/SAMEORIGIN。
   - 缺少 Referrer-Policy 配置。
   - 缺少 Permissions-Policy 配置。

## 3.6 网站化能力缺口（若目标是公网成熟站点）

1. **SEO 优化不足**（新增）
   - 缺少结构化数据（Schema.org JSON-LD）。
   - 缺少 Open Graph 标签（og:title, og:description, og:image 等）。
   - 缺少 Twitter Card 标签。
   - 缺少 canonical URL 配置。
   - 缺少 sitemap.xml。
   - 缺少 robots.txt。
   - Meta keywords 已被主流搜索引擎忽略，但 description 仍需优化。
   - 缺少语义化 HTML 标签（header, nav, main, article, section 等）。

2. **可访问性（a11y）体系未系统化**
   - 缺少 WCAG 2.1 合规性审计。
   - 缺少 ARIA 属性支持。
   - 缺少键盘导航优化。
   - 缺少屏幕阅读器支持。
   - 缺少颜色对比度检查。
   - 缺少焦点管理机制。

3. **静态资源优化与缓存策略不足**
   - 缺少构建产物哈希、按需加载、长缓存策略等现代前端优化能力。

## 3.7 国际化（i18n）缺口（新增）

1. **无多语言支持架构**
   - 所有 UI 文本硬编码在代码中。
   - 无语言切换机制。
   - 无语言资源文件管理。

2. **缺少国际化基础设施**
   - 无 i18n 库集成（如 vue-i18n）。
   - 无语言检测与自动切换。
   - 无 RTL（从右到左）布局支持。

3. **SEO 多语言缺失**
   - 无 hreflang 标签配置。
   - 无多语言 URL 结构（/en/, /zh/ 等）。

## 3.8 Core Web Vitals 性能指标缺口（新增）

根据 Google 2025 年新基准：

1. **LCP（Largest Contentful Paint）**
   - 目标：< 2.5 秒
   - 当前状态：未监控
   - 潜在问题：同步脚本加载可能阻塞渲染

2. **INP（Interaction to Next Paint）**（替代 FID）
   - 目标：< 200ms
   - 当前状态：未监控
   - 潜在问题：大量计算可能影响交互响应

3. **CLS（Cumulative Layout Shift）**
   - 目标：< 0.1
   - 当前状态：未监控
   - 潜在问题：动态内容加载可能导致布局偏移

## 6. 对当前项目最现实的演进路径

建议采用"**先工程化托底，再渐进式重构**"而非一次性重写：

1. **第一阶段**：不动核心业务算法，只补齐 lint/test/CI/监控基础设施 + Vercel 部署。
2. **第二阶段**：按模块边界平移代码，保持行为一致 + SEO 基础优化。
3. **第三阶段**：框架升级与构建体系迁移 + 国际化支持。
4. **第四阶段**：性能优化与可访问性完善。

这样可以避免"重构即停更"，也能保证现有用户持续可用。

## 7. Vercel 部署配置建议

### 7.1 vercel.json 基础配置

```json
{
  "version": 2,
  "public": true,
  "cleanUrls": true,
  "trailingSlash": false,
  "headers": [
    {
      "source": "/(.*)",
      "headers": [
        { "key": "X-Content-Type-Options", "value": "nosniff" },
        { "key": "X-Frame-Options", "value": "DENY" },
        { "key": "X-XSS-Protection", "value": "1; mode=block" },
        { "key": "Referrer-Policy", "value": "strict-origin-when-cross-origin" }
      ]
    },
    {
      "source": "/Scripts/(.*)",
      "headers": [
        { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }
      ]
    }
  ]
}
```
