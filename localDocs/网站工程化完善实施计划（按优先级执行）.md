# 网站工程化完善实施计划（按优先级执行）

版本：v1.0  
日期：2026-03-19  
适用项目：DSQ（静态前端工具站）

## 1. 目标与执行原则

本计划用于将当前“功能成熟的工具站”逐步提升为“可持续维护的成熟网站工程”。

执行原则：

1. 先托底再重构：先补齐工程化基础（质量门禁、CI、测试底座、监控），再做代码结构拆分。
2. 小步快跑：每一步都可独立验证、可回滚、可发布。
3. 不中断业务：核心计算与蓝图功能在全程保持可用。
4. 以验收结果为导向：每个任务必须有明确产出物与验收标准。

---

## 2. 优先级总览（执行顺序）


| 阶段  | 优先级 | 建议周期 | 阶段目标        | 完成判定                    |
| --- | --- | ---- | ----------- | ----------------------- |

## 3. 阶段A（P0）详细计划：先保稳定与协作效率

## A-01 建立 Node 工程脚手架（最高优先）

- 目标：统一脚本入口，消除"手工执行"不一致。
- 具体动作：

1. 新增 `package.json`（脚本只做工程编排，不改业务运行形态）。
2. 增加 npm scripts：`lint`、`format:check`、`smoke`、`ci:check`。
3. 锁定 Node 版本（`.nvmrc` 或 `engines` 字段）。

- 产出物：`package.json`、锁版本说明文档。
- 验收标准：`npm run ci:check` 本地可一次通过。
- 预计工时：0.5-1 天。
- 依赖：无。
- 完成状态：✅ 已完成（2026-03-19）

## A-02 接入 ESLint + Prettier（并先以低风险策略上线）

- 目标：统一代码风格与基础质量规则，降低未来重构冲突。
- 具体动作：

1. 新增 ESLint 与 Prettier 配置。
2. 第一阶段采用"增量约束"策略：旧代码允许 warning，新改代码严格。
3. 对新增文件开启严格 lint；历史大文件分批治理。

- 产出物：`eslint.config.js`（ESLint 9 flat config）、`.prettierrc`、`.prettierignore`。
- 验收标准：`npm run lint` 可稳定运行并输出可读结果。
- 预计工时：1-1.5 天。
- 依赖：A-01。
- 完成状态：✅ 已完成（2026-03-20）

## A-03 配置 Git Hooks 质量门禁（pre-commit / pre-push）

- 目标：在提交前阻断明显问题，减少坏代码进入主分支。
- 具体动作：

1. 配置 `.husky/pre-commit`：执行 `lint-staged`（或最小 lint 检查）。
2. 配置 `.husky/pre-push`：执行 `npm run ci:check` 或最小 smoke。
3. 添加失败提示文案，便于团队成员快速定位问题。

- 产出物：`.husky/pre-commit`、`.husky/pre-push`、`lint-staged` 配置。
- 验收标准：

1. 提交含错误代码会被拦截。
2. 正常提交流程耗时可接受（建议 < 60 秒）。

- 预计工时：0.5-1 天。
- 依赖：A-01、A-02。

## A-04 建立最小 CI（自动执行质量检查）

- 目标：让“是否可合并”由机器判定，不依赖人工口头确认。
- 具体动作：

1. 新增 CI 配置（如 GitHub Actions）。
2. 流程：安装依赖 -> lint -> smoke。
3. 为 PR 增加状态检查规则（必须通过才能合并）。

- 产出物：`.github/workflows/ci.yml`（或同类配置）。
- 验收标准：

1. 任意 PR 自动触发。
2. 失败时能定位到具体步骤和日志。

- 预计工时：0.5-1 天。
- 依赖：A-01、A-02。

## A-05 建立全局错误捕获与关键链路埋点

- 目标：从“靠感觉排错”升级为“有数据可排错”。
- 具体动作：

1. 增加 `window.onerror` 与 `unhandledrejection` 统一处理。
2. 对蓝图生成链路增加耗时、成功率、失败原因统计。
3. 本地先落控制台/本地存储日志，后续再接监控平台。

- 产出物：错误处理模块、埋点说明文档。
- 验收标准：

1. 手动构造异常可被捕获。
2. 蓝图生成可输出耗时统计。

- 预计工时：1 天。
- 依赖：无（可与 A-02 并行）。

### 阶段A里程碑验收

1. 新人拉仓后按文档可在 30 分钟内完成本地检查流程。
2. 提交与PR都具备自动质量门禁。
3. 蓝图核心路径具备最小可观测能力。

## 4. 阶段B（P1）详细计划：可维护性与可测试性

## B-01 拆分 `data.js`（先拆边界，不改行为）

- 目标：降低单文件复杂度，建立可维护模块边界。
- 拆分目标模块：

1. `state`：状态对象与读写。
2. `calc-core`：纯计算逻辑。
3. `ui-bindings`：DOM 与事件绑定。
4. `storage`：localStorage/cookie 读写。
5. `bootstrap`：初始化流程。

- 产出物：新模块目录与迁移说明。
- 验收标准：拆分前后关键功能行为一致（人工回归 + 测试）。
- 预计工时：3-5 天。
- 依赖：阶段A完成。

## B-02 拆分 `blueprint.js`（模型/布局/序列化分层）

- 目标：降低蓝图引擎改动风险，提高定位效率。
- 拆分目标模块：

1. `model`：数据结构与实体定义。
2. `layout`：建筑与传送带布局算法。
3. `serializer`：蓝图编码/压缩。
4. `constants`：常量与映射数据。

- 产出物：模块化后的蓝图引擎目录。
- 验收标准：同一输入生成结果一致（可接受浮点误差范围需提前定义）。
- 预计工时：4-6 天。
- 依赖：阶段A完成。

## B-03 建立单元测试底座（优先覆盖纯函数）

- 目标：保障后续重构可安全进行。
- 具体动作：

1. 引入测试框架（建议 Vitest）。
2. 先覆盖高价值纯函数：配方换算、产量计算、参数转换。
3. 建立“回归样例集”（固定输入/输出）。

- 产出物：测试目录、首批测试用例。
- 验收标准：核心计算模块覆盖率达到可用基线（建议 40%+，核心函数 70%+）。
- 预计工时：2-4 天。
- 依赖：A-01。

## B-04 建立关键流程集成测试

- 目标：验证“用户操作链路”稳定性。
- 首批链路建议：

1. 新增需求 -> 触发计算 -> 展示结果。
2. 修改配置项 -> 结果更新。
3. 蓝图生成 -> 返回文本/复制链路。

- 产出物：集成测试脚本。
- 验收标准：关键链路可在 CI 稳定执行。
- 预计工时：2-3 天。
- 依赖：B-01、B-03。

### 阶段B里程碑验收

1. `data.js` 与 `blueprint.js` 不再是单体超大文件。
2. 核心计算具备自动回归能力。
3. 重构时可用测试与CI兜底。

## 5. 阶段C（P2）详细计划：成熟网站能力建设

## C-01 引入现代构建体系（Vite）

- 目标：获得分包、哈希、压缩、缓存控制能力。
- 具体动作：

1. 建立 Vite 入口，不一次性重写业务。
2. 逐步迁移脚本依赖加载方式。
3. 生成产物使用 hash 文件名。

- 产出物：`vite.config.*`、构建脚本、产物目录。
- 验收标准：`build` 产物可部署并与现有功能等价。
- 预计工时：3-5 天。
- 依赖：阶段B。

## C-02 安全治理与依赖升级策略

- 目标：降低第三方依赖与前端注入风险。
- 具体动作：

1. 建立依赖扫描（Dependabot/SCA）。
2. 增加安全头策略（CSP、权限策略等，按部署环境落地）。
3. 制定 Vue/jQuery 升级或隔离路线图。

- 产出物：安全基线文档、依赖升级清单。
- 验收标准：形成可执行的季度升级节奏。
- 预计工时：2-4 天。
- 依赖：C-01。

## C-03 可观测性平台化

- 目标：形成错误、性能、业务指标闭环。
- 具体动作：

1. 接入前端监控平台（错误与性能）。
2. 定义并看板化核心SLO：蓝图成功率、平均耗时、P95耗时。
3. 加入版本维度分析（按发布版本查看故障变化）。

- 产出物：监控配置、SLO说明、告警策略。
- 验收标准：出现异常可在 10 分钟内定位到版本与链路。
- 预计工时：2-3 天。
- 依赖：A-05。

### 阶段C里程碑验收

1. 项目具备标准构建与部署工艺。
2. 安全与依赖治理进入常态化。
3. 线上质量可通过指标持续优化。

## 9. 风险与应对


| 风险            | 表现      | 应对策略             |
| ------------- | ------- | ---------------- |
| 旧代码 lint 报错过多 | 首次接入阻力大 | 采用增量治理，不一次性清历史债务 |
| 拆分引发行为回归      | 结果计算偏差  | 先补测试，再拆模块，保留回归样例 |
| CI 过慢影响效率     | 提交等待时间长 | 分层执行：快速检查与完整检查分离 |
| 监控噪音太大        | 告警泛滥    | 先定义核心指标与阈值，再扩展维度 |


---

## 10. 完成定义（Definition of Done）

每个任务完成必须同时满足：

1. 有代码或配置产出。
2. 有可执行验收结果（命令、日志或测试报告）。
3. 有变更说明与回滚方式。
4. 不破坏现有核心功能（计算与蓝图生成）。
