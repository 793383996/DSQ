## 二、系统初始化流程深度分析

### 2.1 老代码初始化流程

```
index.html 加载
    │
    ├── <script src="data.js"> 同步加载
    │       │
    │       ├── var data = [...] 立即执行
    │       │
    │       ├── function update_all() {...} 函数声明
    │       │
    │       └── new Vue({...}) Vue实例化
    │               │
    │               └── mounted: function() {
    │                       f_initData()      // 处理data数组
    │                       f_initSettings()  // 初始化设置
    │                       update_all()      // 首次计算
    │                   }
    │
    └── 页面渲染完成
```

**问题分析**:

1. **同步阻塞**: `<script>` 标签同步加载，阻塞页面渲染
2. **全局污染**: 所有变量直接挂载到 `window` 对象
3. **初始化顺序依赖**: `f_initData()` 必须在 `update_all()` 之前执行
4. **无错误恢复**: 初始化失败后无重试机制

### 2.2 新代码初始化流程

```

    │
    ├── initLogger()                    // 日志初始化

    │
```

**改进点**:

## 三、性能瓶颈深度分析

### 3.1 已识别的性能瓶颈

#### P1: 配方数据加载延迟

**问题描述**:

- 老代码: 配方数据内嵌在 `data.js` 中，同步加载
- 新代码: 配方数据独立为 `recipes.json`，需要异步加载

**影响范围**:

- 首屏加载时间增加 50-200ms
- 用户可能在数据加载完成前触发计算

**现有优化**:

```typescript
// RecipeDataService.ts
async initialize(): Promise<void> {
  if (this.initialized) return
  if (this.initPromise) return this.initPromise  // 防止重复初始化

  this.initPromise = this.doInitialize()
  return this.initPromise
}
```

**建议优化**:

1. 使用预加载: `<link rel="preload" href="recipes.json">`
2. 数据分片: 按需加载配方数据
3. Service Worker 缓存: 离线可用

#### P2: 计算结果缓存效率

**问题描述**:

- `CalculatorWorkerService` 实现了 LRU 缓存
- 缓存命中率统计显示优化效果

**现有实现**:

```typescript
// CalculatorWorkerService.ts
private resultCache: LRUCache<string, IWorkerResult> = new LRUCache(50, 5 * 60 * 1000)

// 缓存命中日志
logger.log(`[CalculatorWorkerService] Cache hit (${this.cacheHits}/${this.cacheHits + this.cacheMisses})`)
```

**优化建议**:

1. 增加缓存容量到 100 条
2. 实现持久化缓存 (IndexedDB)
3. 添加缓存预热机制

#### P3: 状态同步频率

**问题描述**:

- Store 到 Legacy 的状态同步可能过于频繁
- 每次状态变更都触发同步

**现有优化**:

```typescript
// stores/blueprint.ts
const SYNC_DEBOUNCE_MS = 16 // 约60fps

function debouncedSyncToLegacy(): void {
  if (syncDebounceTimer) clearTimeout(syncDebounceTimer)
  syncDebounceTimer = setTimeout(() => {
    syncDebounceTimer = null
    doSyncToLegacy()
  }, SYNC_DEBOUNCE_MS)
}
```

**优化建议**:

1. 使用 requestAnimationFrame 替代 setTimeout
2. 实现差异同步，只传输变更部分

## 四、流程缺陷深度分析

### 4.1 已修复的流程缺陷

#### F1: outMap 消费逻辑缺失 (P0-1)

**问题描述**:
老代码 `loadNumber` 中存在 `outMap` 消费逻辑，用于处理副产品抵消需求，新代码初期缺失此逻辑。

**老代码逻辑**:

```javascript
// calculator.js
var outValue = findOut(q.name)
if (outValue !== null && outValue < 0) {
  var absOut = Math.abs(outValue)
  if (absOut >= r) {
    addOut(q.name, r)
    continue  // 副产品完全抵消需求
  } else {
    addOut(q.name, absOut)
    r = r - absOut  // 部分抵消
  }
}
```

**修复方案**:

```typescript
// RecipeCalculator.ts
const outValue = this.findOut(q.name)
if (outValue !== null && outValue < 0) {
  const absOut = Math.abs(outValue)
  if (absOut >= r) {
    this.addOut(q.name, r)
    continue
  } else {
    this.addOut(q.name, absOut)
    r = r - absOut
  }
}
```

#### F2: 机器设置未同步到 Legacy (P0-2)

**问题描述**:
Store 中的 `machineSettings` 变更未同步到遗留代码的全局变量，导致计算使用默认值。

**修复方案**:

```typescript
// bridge.ts
```

#### F3: value2 计算时序错误 (P5-1)

**问题描述**:
老代码先计算 `value2`，再执行 `checkResult`。新代码初期顺序相反，导致溢出检测失效。

**老代码顺序**:

### 4.2 潜在流程风险

#### R1: 递归深度超限处理

**问题描述**:

## 五、时序问题深度分析

### 5.1 已修复的时序问题

#### T1: Legacy 模块加载时序 (P0-3)

**问题描述**:

**修复方案**:

```typescript
// main.ts
async function initializeApp(retryCount: number = 0): Promise<void> {
  try {
    await Promise.race([
      loadLegacyModules(),
      new Promise((_, reject) => setTimeout(() => reject(new Error('Timeout')), 20000))
    ])
    app.mount('#app') // 确保模块加载后再挂载
  } catch (e) {
    if (retryCount < MAX_INIT_RETRIES - 1) {
      await new Promise(r => setTimeout(r, 1000 * Math.pow(2, retryCount)))
      return initializeApp(retryCount + 1)
    }
    // 显示错误页面
  }
}
```

**问题描述**:
`recipeIndexByProduct` 索引可能在计算开始前未构建完成。

**修复方案**:

```typescript
// bridge.ts
function getRecipeIndexReadyPromise(): Promise<void> {
  if (recipeIndexReady) return Promise.resolve() // 已就绪直接返回

  if (!recipeIndexReadyPromise) {
    recipeIndexReadyPromise = new Promise(resolve => {
      recipeIndexReadyResolve = resolve
```

### 5.2 潜在时序风险

#### R3: Worker 初始化竞态

**问题描述**:
多个计算请求可能在 Worker 初始化完成前发起。

**现有保护**:

```typescript
// CalculatorWorkerService.ts
async init(options): Promise<void> {
  if (this.status === 'ready' && this.workerChecksum &&
```

- 错误状态未重置

```typescript
private handleError(e: ErrorEvent): void {

  this.initReject = null
}
```

#### L2: 临界光子速度修正 (P10-1)

**问题描述**:
临界光子的生产速度受射线接收塔等级和增产剂影响，需要特殊处理。

**修复方案**:

```typescript
// UpdateAllService.ts
private fixCriticalPhotonSpeed(...): void {
  const gzSpeedSetting = settingsTime['射线接收塔']
  let fixedGzSpeed: number

  if (gzSpeedSetting !== undefined && gzSpeedSetting > 0) {
    fixedGzSpeed = gzSpeedSetting  // 用户手动输入
  } else {
    // 根据增产剂计算
    if (accValue === '加速') {
      switch (accType) {
        case '增产剂Mk.Ⅰ': fixedGzSpeed = 15; break
        case '增产剂Mk.Ⅱ': fixedGzSpeed = 18; break
        case '增产剂Mk.Ⅲ': fixedGzSpeed = 24; break
        default: fixedGzSpeed = 12
      }
    } else {
      fixedGzSpeed = 12
    }
  }

  // 设置缓存
  calculationCacheService.setCriticalPhotonCache(
    hasLensInput ? 60 / fixedGzSpeed : 10,
    hasLensInput ? 0.1 / fixedGzSpeed : null
  )
}
```

#### L3: checkResult 溢出检测 (P11-2)

**问题描述**:
`checkResult` 函数检测产出溢出并调整 `value2`，逻辑复杂且容易出错。

**老代码逻辑**:

```javascript
function checkResult() {
  function isOverflow(item, info, nn) {
    for (var j = 0; j < item.s.length; j++) {
      var out = findOut(item.s[j].name)
      if (out === null) return false
      var mn = ((nn * 60) / item.t) * info.speed * (item.s[j].n || 1)
      if (out > -1 * mn) return false
    }
    return true
  }

  while (isOverflow(item, info, nn) && xh.value2 > 0) {
    xh.value2 -= nn
    // 添加产出...
  }
}
```

**修复方案**:
完全对齐老代码逻辑:

```typescript
// RecipeCalculator.ts
checkResultWithMachineInfo(
  getMachineInfo: (recipe: IRawRecipe) => IMachineInfo,
  settingsPf: Record<string, string | number>,
  settings: Record<string, { accType?: string; accValue?: string }>,
  defaultAccValue: string
): void {
  const isOverflow = (item: IInternalRecipe, info: IMachineInfo, nn: number): boolean => {
    for (let j = 0; j < item.s.length; j++) {
      const out = this.findOut(item.s[j].name)
      if (out === null) return false
      const mn = ((nn * 60) / info.t) * info.speed * (item.s[j].n || 1)
      if (out > -1 * mn) return false
    }
    return true
  }

  // 与老代码完全一致的while循环逻辑
  while (isOverflow(item, machineInfo, nn) && (xh.value2 || 0) > 0) {
    // ...
  }
}
```

### 6.2 潜在逻辑风险

#### R5: 增产剂效果计算

**问题描述**:
增产剂有"加速"和"增产"两种效果，计算逻辑分散在多处。

**现有逻辑**:

```typescript
// getAccSpeed 函数
function getAccSpeed(type: string, value: string): number {
  if (value === '加速') {
    if (type === '增产剂Mk.Ⅰ') return 1.25
    if (type === '增产剂Mk.Ⅱ') return 1.5
    if (type === '增产剂Mk.Ⅲ') return 2
  } else if (value === '增产') {
    if (type === '增产剂Mk.Ⅰ') return 1.125
    if (type === '增产剂Mk.Ⅱ') return 1.2
    if (type === '增产剂Mk.Ⅲ') return 1.25
  }
  return 1
}
```

**风险**:

- 增产剂效果值硬编码在多处
- 未来游戏更新可能导致不一致

**建议改进**:

```typescript
// 统一配置
const PROLIFERATOR_CONFIG = {
  '增产剂Mk.Ⅰ': { speedBonus: 1.25, productivityBonus: 1.125, consumption: 12 },
  '增产剂Mk.Ⅱ': { speedBonus: 1.5, productivityBonus: 1.2, consumption: 24 },
  '增产剂Mk.Ⅲ': { speedBonus: 2, productivityBonus: 1.25, consumption: 60 }
}

function getProliferatorEffect(type: string, mode: 'speed' | 'productivity'): number {
  const config = PROLIFERATOR_CONFIG[type]
  return mode === 'speed' ? config.speedBonus : config.productivityBonus
}
```

#### R6: 配方优先级选择

**问题描述**:
同一产物可能有多个配方，选择逻辑涉及 `settingsPf` 和 `noExtra` 检查。

**现有逻辑**:

```typescript
// find 函数
const pf = settingsPf[name]
if (pf !== undefined) {
  return getRecipe(this.recipes[pfValue]) // 用户指定优先
}

// 遍历索引
for (const idx of indices) {
  const item = this.recipes[idx]
  const accValue = settings[item.id]?.accValue || defaultAccValue
  if (accValue === '增产' && item.noExtra) continue // 跳过不可增产配方
  return getRecipe(item)
}
```

**风险**:

- 用户可能不知道有多个配方可选
- 默认选择可能不是最优解

## 九、改进建议

### 9.1 架构层面

1. **完全移除 Legacy 依赖**
   - 当前架构仍依赖 `legacy/data.js` 和 `legacy/calculator.js`
   - 建议在 Phase 9 完成后完全移除
   - 使用 `RecipeCalculator.ts` 作为唯一计算引擎

2. **统一状态管理**
   - 当前 Store 和 Legacy 全局变量并存
   - 建议完全迁移到 Pinia Store
   - 移除 `window.xqs`、`window.ig_names` 等全局变量

3. **Worker 计算成为默认**
   - 当前 Worker 为可选
   - 建议默认使用 Worker 计算
   - 仅在不支持 Worker 的环境回退到主线程

### 9.2 性能层面

1. **数据预加载**

   ```html
   <link rel="preload" href="/src/core/data/recipes.json" as="fetch" crossorigin />
   ```

2. **缓存持久化**

   ```typescript
   // 使用 IndexedDB 持久化计算结果
   const cacheDB = await openDB('dsp-calculator', 1, {
     upgrade(db) {
       db.createObjectStore('results')
     }
   })
   ```

3. **差异同步**
   ```typescript
   // 只同步变更的状态
   function syncDiff(oldState, newState) {
     const diff = {}
     for (const key in newState) {
       if (oldState[key] !== newState[key]) {
         diff[key] = newState[key]
       }
     }
     return diff
   }
   ```

### 9.3 可靠性层面

1. **计算取消机制**

   ```typescript

   }
   ```

   ```typescript

     throwOnStateChange: true // 默认 true
   ```
