# 网站完善实施计划

版本：v1.4  
日期：2026-03-25  
适用范围：DSQ 当前代码基线（`index.html + Scripts/*`）

## 0. 执行结论（先看这里）

1. `index.html` 可以拆分，且应优先做“结构与交互控制器拆分”，再做 Vue 组件化。  
2. 当前最影响体验与可维护性的点：
- `UIselector` 缺键盘焦点治理与对话框语义。
- `MoreSetting` 开合由 `show/hide + setTimeout` 驱动，动画生硬且状态易不同步。
- 入口脚本同步加载较重，首屏阻塞风险高。
3. Vue 组件化可行，但建议“渐进迁移”，不建议一次性重写。
4. 主键策略当前保持“中文主键 + 显示层翻译”，本阶段不做全量键值重构。

## 2. `index.html` 结构与功能详细分析

## 2.1 结构复杂度快照（当前）

| 指标 | 当前值 | 说明 |
| ---- | ---- | ---- |
| `index.html` 行数 | 473 行 | 单文件承载职责偏多 |
| `<script src>` 数量 | 25 个 | 均为同步加载，存在首屏阻塞风险 |
| 脚本总大小（未压缩） | 599,727 bytes | 约 586KB 级别，需分级加载 |
| `style=` 内联样式 | 68 处 | 样式治理与复用成本高 |
| `data-i18n*` 标记 | 137 处 | 国际化覆盖较完整 |
| `id=` 数量 | 84 个 | 直接 DOM 绑定点较多 |
| `data.ui-bindings.js` 中 `$(...)` 使用 | 106 次 | jQuery 绑定强耦合明显 |
| `update_all()` 触发点（显式） | 多处高频 | 输入/配置变化易触发全量重算 |

## 2.2 结构分区（按职责）

| 区域 | 关键节点 | 当前职责 | 主要实现 |
| ---- | ---- | ---- | ---- |
| Head/SEO 区 | `canonicalLink`、`metaOgUrl`、schema 脚本位 | 多语言 SEO 元信息 | `Scripts/i18n.js` 动态刷新 |
| 顶部控制区 | `#txtnumber`、`#selmaince`、`#btnAddRequirement` | 需求输入、方案动作入口 | `index.events.js` + `data.ui-bindings.js` |
| 参数控制区 | `#selmodein/#furnace/#chemical/#accType/#accValue/#research` | 全局工艺配置 | jQuery `.change()` 驱动 `update_all()` |
| 弹层区 | `#UIselector`、`#Split`、`#MoreSetting` | 物品选择、多配方、参数面板 | `data.ui-bindings.js` 直接 show/hide |
| 结果渲染区 | `#result`（Vue） | 需求、结果表、合计、说明 | Vue2 模板 + 计算结果绑定 |
| 页脚区 | 法律/安全链接 | 合规入口 | `i18n.js` 根据语言改链接 |

## 2.3 功能主链路（按用户路径）

1. 启动链路：
- `index.html` 同步加载脚本
- `data.bootstrap.js` 异步拉取 `Scripts/data.json`
- `f_init()` 创建 Vue 实例
- `f_initIcons()` 构建图标选择器 DOM

2. 计算链路：
- 新增需求 (`f_add/f_add3`) -> `loadNumber` 递归计算 -> `checkResult` -> `update_all`
- Vue 列表与总计区域更新

3. 配置链路：
- 各下拉/复选框 `.change()` -> 写 `settings/settingsLocal` -> `update_all`

4. 蓝图链路：
- 点击生成 -> `getRecipe` -> `BlueprintFacade.generateAsync` -> Worker/主线程 -> 复制

5. 国际化与 SEO 链路：
- 切语言 -> `dsq:locale-changed` -> 文案刷新 + `update_all` + meta/schema 同步

## 2.4 当前痛点（拆分与性能）

1. 入口职责过重：结构、脚本顺序、交互容器集中在 `index.html`，改动风险大。  
2. 交互控制分散：弹层状态散落在多个 click/change 回调，缺统一控制器。  
3. 全量重算频繁：多个输入事件直接触发 `update_all`，缺批处理/节流。  
4. 首屏加载重：25 个同步脚本 + 大型 `data.json`（1.63MB）会拖慢可交互时间。  
5. 可访问性边缘缺口：`UIselector` 键盘与焦点治理不足，`MoreSetting` ARIA 状态未同步。

## 5. 是否可以拆分成 Vue 组件形式（可行性评估）

## 5.1 结论

可行，且建议执行；但必须采用“渐进迁移”。  
原因：当前页面已存在 Vue2 渲染基础，但仍有大量 jQuery 直接 DOM 操作与全局状态耦合，无法安全一次性切换。

## 5.2 可行性评分

| 维度 | 评分 | 说明 |
| ---- | ---- | ---- |
| 技术可行性 | 8/10 | 已有 Vue/Vite 基础，可逐步组件化 |
| 改造风险 | 6/10 | jQuery 与全局状态耦合较深 |
| 性价比 | 8/10 | 长期维护收益明显 |
| 推荐度 | 高 | 先做边界收敛再组件化 |

## 5.3 推荐组件拆分蓝图

建议目标组件树（可先 Vue2 组件化，再迁移 Vue3 SFC）：

1. `AppShell`
2. `SeoHeaderBridge`（仅管理语言与 SEO 同步）
3. `TopControlBar`
4. `ProcessControlBar`
5. `SettingsPanel`（`MoreSetting`）
6. `ItemSelectorDialog`（`UIselector`）
7. `RecipeSplitDialog`（`Split`）
8. `RequirementList`
9. `ExcludeList`
10. `ResultTable`
11. `TotalSummary`
12. `FooterLinks`

## 5.4 渐进迁移路线（建议）

1. VU-01：先收敛弹层控制器与事件绑定（不改 UI 行为）。
2. VU-02：将 `SettingsPanel` 与 `ItemSelectorDialog` 先组件化（低耦合高收益）。
3. VU-03：迁移结果区（`RequirementList/ResultTable/TotalSummary`）。
4. VU-04：再推进 Vue3 + SFC（若决定进入完整迁移阶段）。

不建议路径：直接整页重写 Vue3（风险高、回归面过大）。

## 6. 主键策略与重构优化计划（新增）

## 6.1 当前执行结论（立即生效）

1. 本阶段维持“中文主键 + 显示层翻译”的现状，不做全量英文/数字主键替换。  
2. 原因：低风险、最快稳定，不影响现有计算链路、本地存档、蓝图生成链路。  
3. 本节新增“未来可选重构路线”，用于后续进入 Vue 深迁移或大版本升级时执行。

## 6.2 已识别影响面（代码扫描结论）

1. 条件判断中直接使用中文字符串的严格命中：83 行（排除 `*.min.js` 与备份文件）。  
2. 主要集中：
- `Scripts/data.ui-bindings.js`：47 行
- `Scripts/data.recipe-init.js`：15 行
- `Scripts/data.recipe-ui.js`：14 行
- `Scripts/data.blueprint.js`：5 行
- `Scripts/calc-core.js`：2 行
3. 关键耦合链路：
- 计算分支：设备、增产剂、特殊配方分支由中文值驱动。
- 索引/查找：`recipeIndexByProduct[name]`、`settings_pf[name]` 等以名称作为键。
- UI/DOM：`data-name`、`data-modein` 参与交互与蓝图解析。
- 存储兼容：`settings/settings_pf/projects` 已有线上与本地历史数据。

## 6.3 若立即全量替换英文/数字主键的主要风险

1. 历史数据失配风险（高）：本地 `localStorage` 旧键无法直接命中。  
2. 配方索引与查找错配风险（高）：`name` 改动会影响 `find/getPfs/getPfsByQ`。  
3. 蓝图链路回归风险（高）：`data-name/data-modein` 被 `data.blueprint.js` 解析使用。  
4. 事件与联动逻辑回归风险（中高）：当前大量判断分支依赖中文枚举值。  
5. 一次性替换回滚成本高（高）：跨文件范围广，难以快速定位单点回退。

## 6.4 推荐目标（未来版本）

1. 引入稳定业务键（建议英文字母数字）：`itemKey/machineKey/accTypeKey/accValueKey`。  
2. 中文名称仅作展示字段（`nameZh`），英文展示字段（`nameEn`）由 i18n 输出。  
3. 业务逻辑与条件判断统一使用稳定 key，不再直接使用显示文案。  
4. 建立兼容映射层：`legacyZhName -> stableKey`，支持平滑迁移。

## 6.5 完整重构路线（分阶段，可回滚）

| 编号 | 阶段 | 目标 | 主要动作 | 验收标准 | 回滚策略 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| KR-00 | 冻结基线 | 维持当前稳定 | 仅做显示层翻译修复，不动主键 | 现有功能与蓝图零回归 | 无需回滚 |
| KR-01 | 键字典引入 | 建立统一实体目录 | 新增 `entityCatalog`（含 stableKey/zh/en/alias） | 目录覆盖现有配方项与设备项 | 可单独移除目录文件 |
| KR-02 | 双轨数据层 | 先兼容后替换 | 数据对象增加 `key` 字段；保留 `name` | 计算结果与当前完全一致 | 保留旧字段优先读取 |
| KR-03 | 逻辑条件替换 | 去除中文判断分支 | `if/switch` 从中文常量迁移到 key 常量 | 条件分支扫描不再出现中文判断 | 切回常量映射到中文 |
